🏛️ Software Architecture คืออะไร?

คำนิยาม

ไม่มีนิยามที่แน่นอนในอุตสาหกรรม บางคนเรียกว่า blueprint ของระบบ บางคนเรียกว่า roadmap สำหรับการพัฒนา

ทำไมถึงสำคัญ?

  • ระบบซับซ้อนขึ้นเรื่อยๆ
  • ความล้มเหลวส่วนใหญ่มาจาก architecture ไม่ใช่ code
  • Architecture จัดการ complexity
💡
Big Picture: CS362 ไม่ใช่แค่เขียน code — แต่คือการออกแบบระบบที่ ทำงานได้, scale ได้, และ รับมือกับการเปลี่ยนแปลงได้

🧠 Architectural Thinking — 4 มุมมองหลัก

1. Architecture vs Design

Traditional view: แยกกัน architect ส่งงานให้ developer

Modern view: ทำงานร่วมกัน — architecture และ design ต้อง sync กันตลอด

"Architecture and design are part of the same lifecycle"

2. Technical Depth vs Breadth

Developer → ต้องการ Technical Depth (เชี่ยวชาญเฉพาะ)

Architect → ต้องการ Technical Breadth (รู้กว้าง, ประเมินตัวเลือกได้)

Knowledge Pyramid: Know → Know you don't know → Don't know you don't know

3. Analyzing Trade-offs

ทุก architectural decision มี trade-offs — ไม่มี "best" solution

"It depends" คือคำตอบที่ถูกต้องใน architecture

ตัวอย่าง: REST vs Message Queue
Small team, simple → REST | High traffic, fault tolerance → Message Queue

4. Understanding Business Drivers

Architect ต้องเข้าใจ business drivers เพื่อแปลงเป็น architecture characteristics:

  • Scalability
  • Performance
  • Availability
  • Security

Lesson 2

Requirements & System Specification

User Stories · Functional vs Non-Functional · Architecture Characteristics

📋 ประเภทของ Requirements

1. Functional Requirements

"What the system must do"

  • User can log in
  • Student can register for courses
  • System calculates payment

2. Non-Functional (NFR)

"How the system must behave"

  • Response time < 2 seconds
  • 10,000 concurrent users
  • 99.9% uptime

3. Constraints

"Limitations to follow"

  • Must use cloud infrastructure
  • Must comply with data protection laws
  • Delivered within 3 months

👤 User Stories

Format มาตรฐาน

As a [type of user],
I want [some goal],
So that [some benefit].

ตัวอย่างที่ดี: "As a student, I want to register for courses, so that I can enroll for the semester."

✅ Good User Stories

  • Focus บน user needs
  • อธิบาย goal ไม่ใช่ solution
  • มี business/user value ชัดเจน
  • ไม่มีรายละเอียด technical

❌ Poor User Stories

  • "As a user, I want microservices." ← technical decision
  • "As a user, I want REST APIs." ← solution ไม่ใช่ need
  • "As a user, I want NoSQL." ← db ไม่ใช่ user concern

⚠️ Common Mistakes

  • ผสม requirements กับ design/technology decisions
  • เขียน requirement ที่ vague เกินไป ("fast", "secure", "scalable")
  • Focus แค่ functional requirements ละเลือง NFR
  • เขียน user stories จากมุมมอง system/developer ไม่ใช่ user
  • กำหนด solution ก่อนเข้าใจ business problem จริงๆ

Lesson 4

Architecture Styles + Design Principles

Monolithic · Distributed · SOLID · Cohesion · Coupling

🏗️ Architecture Styles Overview

Group 1: Monolithic

Deploy เป็น single unit

  • Layered (N-Tier)
  • Pipeline (Pipe & Filter)
  • Microkernel (Plug-in)

Group 2: Distributed

Deploy หลาย units สื่อสารผ่าน network

  • Event-Driven (EDA)
  • Microservices
  • Space-Based
  • SOA

📚 Layered Architecture (N-Tier)

Architecture ที่พบมากที่สุด — แบ่งเป็น horizontal layers แต่ละ layer มี role ชัดเจน

Presentation Layer
↓
Business/Application Layer
↓
Data Access Layer
↓
Database
Advantages
  • Easy to organize teams
  • Clear separation of concerns
  • Each layer testable independently
Disadvantages
  • Architecture Sinkhole — requests pass through with no logic
  • Scale ต้องทำทั้ง monolith
  • Agility ต่ำ — เปลี่ยน feature ต้องแก้ทุก layer

🔧 Pipeline Architecture (Pipe and Filter)

Concept

Data ไหลผ่าน series of transformations — Filters (processing units, stateless) คั่นด้วย Pipes (channels)

Input
→
Filter A
→
Filter B
→
Output

ตัวอย่าง: cat file.txt | grep "error" | awk '{print $1}' · ETL tools (Apache NiFi)

Advantages
  • Reusability — เรียง filters ใหม่ได้
  • Extensibility — เพิ่ม filter โดยไม่แตะ existing
  • Parallelism
Disadvantages
  • Performance overhead (serialization)
  • Error handling ยาก
  • Branching logic ซับซ้อน

🔌 Microkernel Architecture (Plug-in Pattern)

Components

  • Core System — minimal "happy path" logic
  • Plug-in Registry — รู้ว่า plug-ins มีอะไร
  • Plug-in Modules — specialized features, follow contract (interface)

ตัวอย่าง: VS Code — core คือ text editor, ที่เหลือเป็น plug-in ทั้งหมด

Advantages
  • High Extensibility
  • Bug ใน plug-in ไม่ crash core
  • Update plug-ins runtime ได้
Disadvantages
  • Core Bloat เมื่อเวลาผ่านไป
  • Contract rigid เปลี่ยนยาก
  • Inter-plugin communication ยาก

⚡ Event-Driven Architecture (EDA)

Core Idea

Systems react to events แทนการ call กันโดยตรง — Producer ไม่รู้จัก Consumer

🔬 Microservices Architecture

Core Principles

  • Database per Service — แต่ละ service มี DB ของตัวเอง
  • Bounded Context — logic แยกตาม business function
  • Independent Deployment — deploy แยกกันได้

ตัวอย่าง: Netflix — thousands of microservices (Continue Watching, User Profile, Video Streaming ฯลฯ)

Advantages
  • Independent Deployment
  • Scale เฉพาะ service ที่ต้องการ
  • Fault Isolation
Disadvantages
  • Operational Complexity (Docker/K8s)
  • Distributed Tax (network latency)
  • Data Integrity across DBs

🏛️ Space-Based & SOA

Space-Based Architecture

แก้ปัญหา "Database Bottleneck" — ประมวลผลใน RAM

  • Processing Unit (code + in-memory grid)
  • Virtual Middleware (replication)
  • Data Pump (async → DB)

ตัวอย่าง: Ticketmaster — คนกด "Buy" พร้อมกันหลายพัน

SOA (Service-Oriented Architecture)

"บรรพบุรุษ" ของ Microservices — focus บน reusability ระดับ enterprise

  • ESB (Enterprise Service Bus) เป็นศูนย์กลาง
  • เชื่อม legacy systems กับ modern apps
+
  • Reusability
  • Interoperability
−
  • ESB = single point of failure
  • Performance bottleneck

⚙️ SOLID Principles

💡
Architecture styles กำหนด "where" — Design principles กำหนด "how" ในการ implement
S

Single Responsibility Principle (SRP)

A class should have one reason to change — หนึ่ง class หนึ่งหน้าที่

❌ UserService ทั้ง authenticate + send email + log = ผิด | ✅ แยกเป็น AuthService, EmailService, LogService
O

Open/Closed Principle (OCP)

Open for extension, Closed for modification — เปิดให้ขยาย แต่ปิดไม่ให้แก้ code เดิม

ใช้ abstraction/polymorphism — เพิ่ม feature ใหม่โดยสร้าง class ใหม่ ไม่แก้ class เดิม
L

Liskov Substitution Principle (LSP)

Subtypes must be replaceable for their base types — class ลูกต้องใช้แทน class แม่ได้ โดยไม่ทำให้ระบบพัง

❌ Square extends Rectangle แล้วทำให้ area calculation ผิด = ละเมิด LSP
I

Interface Segregation Principle (ISP)

Clients should not depend on interfaces they don't use — อย่าบังคับให้ class implement สิ่งที่ไม่ใช้

แบ่ง interface ใหญ่เป็นหลาย interface เล็กที่ specific
D

Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules — ทั้งคู่ต้อง depend on abstraction

อย่าผูกกับ concrete class ให้ผูกกับ interface/abstraction แทน
PrincipleCore IdeaKey Benefit
SRPOne class, one responsibilityEasier to maintain
OCPOpen for extension, closed for modificationEasy to extend without breaking
LSPSubclasses replace parent safelyCorrect inheritance
ISPSmall, focused interfacesNo unnecessary dependencies
DIPDepend on abstractionsFlexible and testable
Lesson 5

Design Patterns

Gang of Four · Creational · Structural · Behavioral

📖 History & Background

Origin

1977: Christopher Alexander เขียน A Pattern Language — patterns ใน urban design

1994: Gang of Four (Gamma, Helm, Johnson, Vlissides) ประยุกต์ใช้กับ OOP → หนังสือ Design Patterns: Elements of Reusable Object-Oriented Software

Key Idea

Patterns ไม่ได้ "invent" — ถูก discover เมื่อ solution สำเร็จซ้ำๆ หลายโปรเจกต์

Blueprints, not code — เป็น template ไม่ใช่ finished code

"Design patterns are not code you copy, but design ideas that help you build better software."

🗂️ 3 Categories

Creational

How objects are created

  • Singleton
  • Factory Method
  • Abstract Factory
  • Builder
  • Prototype

Structural

How classes/objects are organized

  • Adapter
  • Bridge
  • Composite
  • Decorator
  • Facade
  • Proxy

Behavioral

How objects communicate

  • Observer
  • Strategy
  • Command
  • State
  • Mediator

✨ Patterns ในหลักสูตร

Creational

Singleton Pattern

Ensures a class has only one instance and provides a global access point

ใช้เมื่อ:
  • ต้องมีแค่ instance เดียวในระบบ (logger, config, DB connection pool)
  • หลาย components ต้องแชร์ resource เดียวกัน
class PrinterSpooler:
    _instance = None

    @classmethod
    def getInstance(cls):
        if cls._instance is None:
            cls._instance = PrinterSpooler()
        return cls._instance

    def print(self, job):
        print(f"Printing: {job}")
Advantages
  • Single instance guaranteed
  • Global access point
  • Resource savings
Disadvantages
  • Global state → hard to manage
  • Tight coupling
  • Unit testing difficult
  • Concurrency issues
Creational

Factory Pattern

Creates objects without exposing creation logic — client ถาม factory ให้สร้างแทน

ใช้เมื่อ:
  • ต้องสร้าง object หลาย types แต่ไม่อยากให้ client รู้ว่าสร้างยังไง
  • Client ไม่ควร depend บน specific classes
class NotificationFactory:
    @staticmethod
    def create(type: str):
        if type == "email":
            return EmailNotification()
        elif type == "sms":
            return SMSNotification()
        elif type == "push":
            return PushNotification()
        raise ValueError(f"Unknown type: {type}")
Advantages
  • Encapsulates creation logic
  • Supports OCP
  • Reduces class dependencies
Disadvantages
  • เพิ่ม number of classes
  • Extra abstraction layer
Behavioral

Observer Pattern

Defines one-to-many relationship — เมื่อ object เปลี่ยน state, ทุก dependents ถูก notify อัตโนมัติ

ใช้เมื่อ:
  • หลาย objects ต้อง react ต่อการเปลี่ยนแปลงของ object หนึ่ง
  • ต้องการ loose coupling ระหว่าง components
class YouTubeChannel:  # Subject
    def __init__(self):
        self._subscribers = []

    def subscribe(self, observer):
        self._subscribers.append(observer)

    def upload(self, video):
        for sub in self._subscribers:
            sub.notify(video)  # auto-notify all
Advantages
  • Loose coupling
  • Auto notification on change
  • Easy to add observers
Disadvantages
  • Unexpected updates if many observers
  • Performance ถ้า observers เยอะ
  • Debug ยาก
Behavioral

Strategy Pattern

Allows selecting algorithm/behavior at runtime — swap strategies โดยไม่แก้ main code

ใช้เมื่อ:
  • มีหลายวิธีทำ task เดียวกัน
  • ต้องการเปลี่ยน behavior dynamically
class PaymentContext:
    def __init__(self, strategy):
        self._strategy = strategy

    def pay(self, amount):
        self._strategy.process(amount)

# Usage
ctx = PaymentContext(CreditCardStrategy())
ctx.pay(500)
ctx._strategy = PromptPayStrategy()  # swap at runtime
ctx.pay(500)
Advantages
  • Encapsulates algorithms
  • Behavior changeable at runtime
  • Follows OCP
  • Reduces if-else chains
Disadvantages
  • เพิ่ม number of classes
  • Client ต้องรู้จัก strategies

🔺 The Design Model Pyramid

4 Levels

  1. Interface Design — จาก Use Case/Sequence Diagrams → API, UI
  2. Architectural Design — จาก Class Diagrams → Layered/MVC structure
  3. Component-Level Design — internal logic แต่ละ module

Three Pillars of Software Design

  • Principles (Philosophy) — SOLID, Quality Attributes

  • Practices (Mechanics) — UML, Git Workflow, folder structure

Lesson 7

Git Workflow

Branch Strategy · Conventional Commits · PR Review · Merge Conflicts

🌿 Branch Structure

main (production-ready)
└── uat (User Acceptance Testing)
    └── sit (System Integration Testing)
        └── develop (integration branch)
            ├── feature/login
            ├── feature/payment
            └── feature/search

🔄 5-Step Development Cycle

1. Pull — อัพเดท develop ให้ล่าสุด

git checkout develop
git pull origin develop

2. Branch — สร้าง feature branch

git checkout -b feature/borrow-book

3. Commit — บันทึก incremental progress

git add .
git commit -m "feat: add borrow book API"

4. Push & PR — upload branch + open Pull Request

git push origin feature/borrow-book
# แล้ว open PR ใน GitHub: feature → develop

5. Review & Merge — teammate review → merge

# Optional: ลบ feature branch หลัง merge
git branch -d feature/borrow-book
git push origin --delete feature/borrow-book

⚠️ Merge Conflicts

กฎสำคัญ

Conflict always เกิดกับคนที่ merge ทีหลัง เพราะทั้งสอง branches แก้ file เดียวกันต่างกัน

วิธีป้องกัน

ก่อน merge feature branch ไป develop เสมอ:

git checkout feature/your-branch
git pull origin develop
# หรือ
git merge develop
# แก้ conflict ใน feature branch ก่อน
# แล้วค่อย merge ไป develop

Conflict Message

CONFLICT (modify/delete):
code.go deleted in develop
and modified in feat/ServiceA

# Aida ต้องตัดสินใจ:
# - Keep code.go
# - Accept deletion
# - Modify
⚡
"Always update your feature branch with the latest develop before merging. Otherwise, the last person who merges will get conflicts."

Format

<type>(optional scope): <description>

feat(auth): add login API

Lesson 8

System Design for Large Systems

Scalability · Caching · Message Queues · DDD · Database Strategies

🔑 4 Key Concerns

Scalability

Can the system handle increasing traffic?

  • Vertical Scaling — เพิ่ม CPU/RAM server เดิม
  • Horizontal Scaling — เพิ่มจำนวน servers + Load Balancer
  • Caching — ลด DB load
  • DB Sharding — แบ่ง DB หลาย partitions

Maintainability

How easy is it to update and extend?

  • Modular Design (Microservices)
  • Clear API Documentation

Reliability

Does the system stay available under failures?

  • Fault tolerance: retries, failovers, backups
  • High availability + distributed system
  • Standby load balancer

Performance

How fast and efficient is the system?

  • Optimized DB queries + indexing
  • Asynchronous processing
  • Caching (Redis, CDN)

⚡ Caching Strategies

Redis (In-Memory Cache)

  • Speeds up DB queries & API responses
  • อ่านจาก RAM เร็วกว่า disk ~1000x
  • ใช้กับข้อมูลที่ read บ่อย เปลี่ยนไม่บ่อย

CDN (Content Delivery Network)

  • Cache static content (images, videos, scripts)
  • Serve จาก edge node ใกล้ user
  • ลด latency, ลด load บน origin server

🏢 Domain-Driven Design (DDD)

💡
DDD = แนวทางพัฒนา software โดยออกแบบตาม business domain และ business logic

1. Ubiquitous Language

ภาษากลางที่ทุกคนใช้ร่วมกัน — Dev, BA, Domain Experts, Testers ใช้คำเดียวกัน

Order, Customer, Payment, Invoice ต้องปรากฏทั้งใน code และ docs

2. Entities

Objects ที่มี unique identity และ lifecycle

  • User
  • Order
  • Product

แม้ data เปลี่ยน identity ยังเดิม

3. Value Objects

Objects ที่ไม่มี identity — defined by values, usually immutable

  • Address
  • Money
  • Email
  • Coordinate

4. Aggregates

กลุ่ม entities/value objects ที่ treat เป็น single unit

Order (Aggregate Root)
├── OrderItem
├── Payment
└── ShippingAddress

5. Repository

ใช้ access และ manage domain objects จาก DB — abstract data access layer

  • UserRepository
  • OrderRepository

6. Domain Services

Business logic ที่ไม่เป็นของ entity ใดเลย

  • PaymentService
  • OrderService
  • NotificationService

DDD Architecture Layers

LayerResponsibility
PresentationControllers, API, UI
ApplicationUse cases, app logic
DomainBusiness logic, domain model
InfrastructureDatabase, external services

When to Use DDD?

  • Large systems
  • Complex business logic
  • Microservices architecture
  • Enterprise: E-commerce, Banking, Logistics, ERP

❌ ไม่จำเป็นสำหรับ simple CRUD applications

📊 Load Testing

คืออะไร?

Simulate expected user traffic — measure behavior under normal load

Goal: Ensure system performs well under realistic load

Key Metrics

  • Response Time (e.g., < 200ms)
  • Throughput (requests/second)
  • Error Rate (% failed requests)
  • CPU / Memory Usage

Why Needed?

  • Validate performance requirements
  • Detect bottlenecks ก่อน production
  • Prevent system failure
  • Without it = guessing performance

Social Media Feed

20,000 concurrent users, heavy read

  • Response < 200ms
  • Feed load < 1 sec

Test: API speed, caching efficiency, DB reads

E-learning Platform

10,000 students, video + quiz

  • Page load < 2 sec
  • Quiz submit < 500ms

Test: Mixed workload, DB, session

Chat Application

1M messages/minute

  • Delivery < 200ms
  • No message loss

Test: MQ performance, horizontal scaling

💥 Stress Testing

คืออะไร?

Push system beyond normal limits — identify breaking point

Goal: Understand behavior under extreme conditions | "Better to fail in testing than production"

Load vs Stress

TypePurpose
Load TestingNormal expected traffic
Stress TestingBeyond system limits

ตัวอย่าง: Ticket booking — expected 10k users, stress test 100k users

What to Validate

  • Auto-scaling capability
  • Queue handling under load
  • Circuit breakers
  • Failover mechanisms
  • Recovery time

🔐 Security Testing

Common Threats

  • SQL Injection
  • Cross-Site Scripting (XSS)
  • Authentication bypass
  • Data leaks
  • Hardcoded credentials
  • Insecure APIs

Types of Security Testing

  • Vulnerability Scanning — find known weaknesses
  • Penetration Testing — simulate real attacks
  • Authentication Testing — login & access control
  • Authorization Testing — permission checks
